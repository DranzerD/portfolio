01 SpendFlowExpense backend: receipts in, approvals, an append-only ledger, payouts that can't happen twice. 1 payout from 24 simultaneous requests Java 21, Spring Boot, PostgreSQL, JWT

A multi-tenant backend where employees submit expenses and receipts. Fields are read off the receipt (Claude when there's an API key, an offline parser when there isn't), a policy engine decides who has to approve, and approved spend posts to a double-entry ledger. Reimbursing is idempotent, so a retry never pays twice.

How it works

  • The tenant id only ever comes from the JWT, and every lookup is scoped by it.
  • Money is integer paise. The ledger rejects unbalanced posts, database triggers make rows immutable, and fixes are reversing entries.
  • Four separate guards against double payment: idempotency keys, row locks, a state-machine check and unique constraints.
  • Receipt extraction is a forced LLM tool call, then a validator re-checks every field. Anything low-confidence goes to a review queue.
  • Receipt jobs run through a database-backed queue with retries, backoff and a dead-letter queue.

Numbers

  • 24 threads, same expense → exactly 1 payout
  • 40 parallel reimbursements → 0 double postings, trial balance balanced
  • Duplicate detection: precision 1.00, recall 1.00 (300 genuine, 60 injected duplicates, 60 hard negatives)
  • 31 tests: unit, HTTP, concurrency, evals

Still rough

No AWS deployment, CI, Dockerfile or frontend yet. The PostgreSQL path has only been run against H2.

02 CampaignFlowTwo Go services: ad serving with hard budgets, and analytics over a RabbitMQ event stream. No overspend under concurrent serving Go, Redis (Lua), RabbitMQ, PostgreSQL, Docker

The Ad Service manages advertisers, campaigns and ads and serves the best eligible ad that's still under budget. The Analytics Service consumes impression and click events from RabbitMQ and reports aggregates. Each service owns its own PostgreSQL database, and everything runs with Docker Compose.

How it works

  • Budget checks are a single Redis Lua script, so they're atomic. A concurrency test proves nothing overspends.
  • Events are delivered at-least-once, so the consumer is idempotent: the event UUID is the primary key with ON CONFLICT DO NOTHING, and the counter increments in the same transaction.
  • Reports are suppressed below 50 impressions, so small groups can't be singled out.
  • Fixed after my own review: a poison-message requeue loop, events lost on cold start, and double-counted clicks (Redis SET NX).

Numbers

  • Concurrency test: no overspend
  • Real-broker end-to-end test covers publish → consume → ack
  • Keyword cache in Redis with TTL and invalidation on writes

03 AlumniConnectAn alumni network where each college's data stays private to its members. 26 API routes, 5 roles, 140 end-to-end checks Next.js 15, React 19, SQLite, JWT

Students, alumni and faculty connect, message, post jobs, run events and set up mentorship. Sign-up needs the college's email domain, and every query is scoped to the user's college. Deployed on Render.

How it works

  • 5 roles, from student to platform admin

04 Text-to-SQL with QLoRAFine-tuned Qwen3-1.7B to write SQL, entirely on a 4 GB laptop GPU. 65.2% → 75.4% execution accuracy PyTorch, PEFT, bitsandbytes, Ollama

A QLoRA fine-tune that turns plain English into SQLite queries. Training, evaluation and deployment all ran on an RTX 3050 laptop GPU. The final model is exported to GGUF and served by Ollama, with a CLI that answers questions about any SQLite file.

How it works

  • I ran every training example against SQLite first. About 20% of the reference queries were broken and got filtered out.
  • It fits in 4 GB with 4-bit quantisation, gradient checkpointing, a paged 8-bit optimiser and gradient accumulation (peak 3.2–3.4 GB).
  • Grading compares result sets, not SQL strings, in sandboxed in-memory databases with timeouts. The grader has its own tests.
  • Confidence intervals, McNemar's paired test, and a data-size ablation from 1k to 8k examples.
  • Showing three example rows per table in the prompt lifted every model by about 12 points.

Numbers

  • Base 65.2% → fine-tuned 75.4% on 500 held-out questions (+10.2 points, p < 1e-6)
  • Gemma 3 4B, twice the size: 69.4%
  • Ollama GGUF export: 76.2%, no accuracy loss
  • Single-join queries 45% → 72%
  • Whole pipeline: about 6 hours on one laptop GPU

Still rough

Trained on a synthetic dataset (Spider and BIRD are next). Window functions are still weak (2 of 18). Read-only queries only.

05 OpsPilotAn AI agent that investigates incidents on a simulated 5-service platform, scored against a rules baseline. 86% top-1 root cause, 92 of 92 citations valid Python, FastAPI, OpenTelemetry, Prometheus, DuckDB

A five-service simulated platform instrumented with OpenTelemetry and Prometheus. A fault injector breaks it in realistic ways (pool exhaustion, latency, timeout misconfig, malformed input, bad deploys) and records the true root cause. An LLM agent with read-only tools and a rules baseline then diagnose every incident, and an eval harness scores both.

How it works

  • Incidents are frozen into Parquet bundles, so every experiment replays identically.
  • A triage step builds a compact briefing, so one investigation costs about 2.5k tokens.
  • The agent has four tools (query_metric, search_logs, get_service_spans, submit_diagnosis) and must cite evidence. I check mechanically that every cited id exists in its evidence ledger.
  • A leak test confirms no recorded telemetry reveals that a fault was injected. The held-out set was scored once, after freezing the prompts.

Numbers

  • Dev set (21 faults, 3 no-fault): 86% with tools vs 76% without
  • 92 of 92 citations valid
  • Held-out set: agent 70%, rules baseline 90%
  • gpt-oss-120b did not beat 20b and used 2–3× the tokens

Still rough

On the held-out set the agent loses to the rules baseline, and latency faults and no-fault runs are its weak spots. Alert grouping, a web console, a Slack bot and remediation approvals from my spec aren't built.

06 Meeting SynthPaste a meeting transcript, get tasks, decisions and sentiment. Then ask across every meeting and get cited answers. Recall@5 1.00, refuses what it can't answer Next.js, FastAPI, ChromaDB, sentence-transformers

A local ML pipeline pulls tasks, decisions, sentiment and a summary out of a transcript. A RAG chat then answers questions across every analysed meeting, citing the meeting, chunk and speaker, and says "I don't know" without calling the LLM when the evidence isn't good enough.

How it works

  • Retrieve, rerank with a cross-encoder, pass a relevance gate, then answer with citations. The LLM provider is swappable (Groq, OpenAI, Anthropic).
  • If the Python service is down, a TypeScript heuristic pipeline takes over.
  • An eval harness measures Recall@K, Precision@K, MRR and refusal accuracy, and benchmarks latency with and without reranking.

Numbers

  • Recall@5 1.00, MRR 0.967 with reranking
  • Refused 5 of 5 unanswerable questions; wrongly refused 0 of 15 answerable ones
  • Task classifier 73.2% F1 (5-fold CV)
  • Reranking costs 140.6 ms vs 12.3 ms without
  • 185 automated tests (106 pytest, 79 Vitest)

Still rough

One shared workspace (no multi-tenancy), meetings stored as JSON files, no claim-level faithfulness check, no streaming.

07 CellSelectML that picks which cellular validation tests to run for a code change, given a lab-time budget. 93.9% of faults caught with 80% less lab time Python, scikit-learn, pytest, GitHub Actions

It predicts which tests are likely to fail for a change, then picks and orders a subset that fits the time budget while keeping mandatory tests and coverage of what changed. It runs against a simulator I wrote of a cellular stack (link budget, CQI/BLER, HARQ, RRC timers, A3 handover, reconnection) with 22 injectable software faults.

How it works

  • Greedy selection by (risk × residual + λ·coverage) / duration, with critical tests always included.
  • Safe fallbacks for thin history, model uncertainty, unseen change types and a missing model.
  • Leakage control: chronological splits, forward-chaining CV, and tests that mutate future data to prove the features don't change.
  • Every pick or skip comes with a human-readable reason.
  • CI runs lint, an Ubuntu/Windows × Python 3.11/3.12 matrix, a smoke pipeline and a benchmark.

Numbers

  • 20% budget: 93.9% of faults vs 85.7% for the best baseline
  • 10% budget: 90.1% vs 76.6%
  • (3 seeds × 120 held-out changes)
  • First failing test after about 367 s, vs 3,573 s for the full suite
  • Selection overhead 130–146 ms; simulator has 160 tests

Still rough

The simulator and data are synthetic, not a real modem or RF chain, and per-execution PR-AUC is modest (about 0.19).

08 FaultlineTurns a day of raw failure logs into a short triage report, published automatically. 1,202 failure lines → 28 signatures Python, Drain3, scikit-learn, Ollama, GitHub Actions

Failure lines are parsed into templates (Drain), embedded, clustered into recurring signatures, classified (new bug, known bug, flaky, environment, noise), summarised by a local LLM through Ollama, and published as HTML to GitHub Pages whenever new logs land.

How it works

  • Runs on about 1M lines of the Loghub BGL supercomputer dataset, which has real alert labels.
  • Time-based train/test split, with tuning only on an inner validation split.
  • A new-signature detector flags alert classes never seen in training.
  • Parser and classifier state is committed, so CI resumes incrementally. LLM summaries are cached per signature.
  • No paid services: public data, local embeddings, local LLM.

Numbers

  • Classifier 96.9% accuracy vs 87.2% baseline
  • Alert precision 1.00, recall 0.92
  • 82.4% on never-seen templates (baseline 21.3%)
  • Signature purity 98.3%
  • Median daily review: 1,202 lines → 28 signatures

09 Wi-Fi Reliability FrameworkA pytest framework that tests Wi-Fi, captures packets and logs, and works out why a test failed. 4 of 4 injected faults diagnosed Python, pytest, Scapy, tc/netem, iptables

It tests latency, loss, DNS, stability and reconnection, captures packet and log evidence around each test, and diagnoses root cause with a 10-rule engine. An optional LLM layer explains the result and flags where it disagrees with the rules instead of overriding them. Runs on Windows, Linux and macOS.

How it works

  • Each of the 10 rules is a pure function with unit tests (weak signal, congestion, DNS, AP deauth, driver drop).
  • Faults are injected for real (tc/netem, iptables, firewall rules) or synthetically, and the report says which one ran.
  • I caught a bug in my own measurement: receive-segment coalescing made a healthy link look like 21% TCP retransmissions. Fixing the detection took that to 0%. A BPF filter fixed capture-scope pollution too.

Numbers

  • Control, weak signal, DNS failure, unexpected drop: 4 of 4 diagnosed correctly
  • False retransmissions 21% → 0% on a healthy link
  • 16 offline rule-engine tests

Still rough

Consumer adapters can't do monitor mode, so the deauth rule can't fire on my hardware. Loss and latency injection is synthetic on Windows. No iperf3 throughput test.
